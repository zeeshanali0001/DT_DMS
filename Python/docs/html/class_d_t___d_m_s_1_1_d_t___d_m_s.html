Detailed Description

The DT_DMS class is the general class of the Digital Twin Data-Models-Services (DT-DMS) framework.

It holds the formal specification of a Digital Twin: 

DT = ⟨ D, M, S, μ ⟩

Key features of the class include:

  • D: the ToI data (DT_Data), D = D_hist ∪ D_rt.
  • M: the models of the ToI (DT_Model), M = M_desc ∪ M_pred ∪ M_presc.
  • S: the DT services (DT_Service), S = S_moni ∪ S_pred ∪ S_diag ∪ S_opti ∪ S_cont, with s : M × Ω_D → Y_s.
  • μ: the model inference or data assimilation function (DT_Mu), μ : Ω_D × M → M.
  • It connects the Data, Models and Services of the Digital Twin and manages the information flow between them: μ observes every data source and updates every model, and each model notifies the services coupled to it.
  • The iterator design pattern over the data, the models and the services (begin_…(), current_…(), next_…(), end_…()).
  • Validity checks of the DT: services versus models, models versus data and data versus services (check_consistency()).
  • The export of its own Data-Models-Services diagram in the Graphviz format (dump_graphviz()).

The components are held by composition: data, models, services and μ are parts of the DT.

Constructs a Digital Twin ⟨D, M, S, μ⟩, in one of three ways (as the Java constructors):

  • DT_DMS(delta): an empty Digital Twin;
  • DT_DMS(name, delta): an empty named Digital Twin;
  • DT_DMS(other): a copy of other, with the same data, models and services. The lists are copied but the components themselves are shared, and so are μ, δ and the clock, so that every datum is still assimilated once into each model.

delta is the freshness threshold δ (same time unit as the data measurement times).

Checks the data characteristics (formats, units, ...) with respect to the services of the DT.

  • Services need data: S ≠ ∅ ⇒ D ≠ ∅.
  • Every data source must be valid (DT_Data.validate_data).
  • Warnings (not errors): a data source without unit, and a monitoring service whose monitored entity is neither the source nor the type of a data source.

◆ check_models_versus_data()

bool DT_DMS.DT_DMS.check_models_versus_data ( self,
TextIO out = sys.stdout,
float epsilon = 1e-3,
float big_m = 0.1 )

Checks the fitting of the data versus the models: for every data source D_i and every model M_j that gives values in time (DT_Model.evaluate), computes δ = |ω(t) − m(t)| over the real-time data of the source.

  • If δ < ε for every datum, the model fits the data very well.
  • If the mean of δ is greater than big_m, the model does not fit the data well and should be updated, re-parameterized or discarded.
  • Otherwise the fitting is acceptable.

Models that give no value in time are skipped.

Parameters
outwhere the report is written.
epsilonthe tolerance ε under which a datum is fitted very well.
big_mthe mean deviation M over which the model does not fit the data.
Returns
False if some model does not fit some data source.

◆ check_services_versus_models()

bool DT_DMS.DT_DMS.check_services_versus_models ( self,
TextIO out = sys.stdout )

Checks the consistency of the services with respect to the models they are coupled to.

  • A coupled model must belong to M.
  • A prediction service coupled to a model needs a predictive model.
  • An optimization or a control service needs a prescriptive model (it cannot run without it).
  • Monitoring and diagnosis services can use any model, or none (data-driven services).
    Parameters
    outwhere the report is written.
    Returns
    True if every service is consistent with its model.
